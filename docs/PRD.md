## 0. 一句话产品定义

把「运营商宽带 → 光猫桥接 → 主路由拨号 → 软路由（下游二级路由）」这条**只保证"能上网"的物理链路**，升级为一套**分层隔离、可运营的家庭私有云**，并把**不可信的上游租客网段纳入边界设计**：

> 对外一张网，软路由下划分两个互不可见的信任域（家庭网 / 家庭私有云），上游租客网段视为不可信边界；其上叠加四项可交付服务——**网络质量优化、智能家居中枢、全域广告过滤、私有存储与自动备份**。

产品的核心不是"装了哪些软件"，而是**隔离机制 + 统一身份 + 自动化闭环**这三件事。

## 1. 现状与问题定义

### 1.1 现状链路

| 层级 | 现状 |
|---|---|
| 出口 | 运营商宽带 → 光猫桥接 → 主路由 PPPoE 拨号 |
| 租客网络 | 出租楼层设备**直接接入主路由**；软路由的 WAN 口也接在同一网段，二者同处一个二层广播域 |
| 软路由 | OpenWrt 24.10 x86_64，Lenovo H3000（Intel Pentium J2900 4 核 / 4GB 内存 / 120GB SSD），双口 2.5GbE 网卡；LAN `192.168.1.1/24`（示例）；已部署 Tailscale 与 Docker |
| 家庭网络 | 家庭成员设备与 IoT 挂在软路由下 |
| NAS | 挂在软路由下，位于内层，需与上游租客网段严格隔离 |

### 1.2 真正的问题

原始需求描述里全是"要什么功能"，缺的是"产品结构"。逐条翻译成产品语言：

| 原始诉求 | 本质问题 |
|---|---|
| 租客网络与自用网络各走各的 | **上游网段不可信**。软路由 WAN 与租客设备同处一个二层广播域，"它在我上一级"不等于安全——ARP 探测与端口扫描可直接打到 WAN 口 |
| 网络分发给多楼层 | 全屋共用一张大平层，**没有分域，就没有分权** |
| 全屋网络加速 | **需求定义不清**。"加速"至少 4 种含义（见 F1），不定义就无法验收 |
| 去广告 | 把两个不同技术战场混为一谈：**DNS 域名层**能拦的和 **App 内嵌广告**拦不到的是两回事 |
| NAS 家庭存储 | 只有"一块盘"。**没有账号、没有配额、没有自动备份闭环**，对家人等于不可用 |
| 内网穿透远程访问 | 属于**能力**而非功能，需要落到具体访问路径（Web / 文件 / 桌面） |

## 2. 目标与成功指标

**北极星指标**：家庭成员在**零技术操作**的前提下，感知到"网更快、更干净、东西更安全"；同时**上游租客网段对软路由下的任何资产零可达**。

| 目标 | 可量化指标 | 验收口径 |
|---|---|---|
| G1 隔离有效 | 越权可达端口数 = 0 | 从上游租客网段扫描软路由 LAN 侧资产（NAS、管理面、家庭设备），全部超时/拒绝 |
| G2 广告过滤 | DNS 层拦截率 ≥ 15%；误杀申诉 < 1% | AdGuard 查询日志统计；误杀需有"一键放行"通道 |
| G3 网络质量 | 内网延迟抖动 < 2ms；DNS 平均解析 < 30ms | 软路由侧持续探测，保留 7 天曲线 |
| G4 备份闭环 | 增量备份成功率 ≥ 99%；接入 WiFi 后 5 分钟内完成 | 以"上次成功时间"为唯一真相，失败必须告警 |
| G5 远程可用 | 外出访问私有云可用性 ≥ 99% | 远程连接成功率 + 有效带宽（受家庭上行带宽封顶） |
| G6 可维护 | 任一变更可在 15 分钟内回滚 | 配置与镜像有版本化备份 |

> G3 中的"加速"最终指标依赖第 9 章 Q1 的定义，未定义前不承诺任何数字。

## 3. 用户与角色

| 角色 | 是谁 | 核心诉求 | 权限边界 |
|---|---|---|---|
| **R0 管理员** | 家庭网络的运维者 | 可运营、可排障、可回滚 | 全域读写；唯一能改网络与服务配置 |
| **R1 家庭成员** | 自住楼层使用者 | 上网快、没广告、能存东西，家里东西外人看不见 | 家庭域 + 自己的私有云目录；**不可达私有云管理面与他人目录** |
| **R2 租客** | 出租楼层住户，**不在软路由管辖内** | 网络独立可用 | 仅互联网；**对软路由下的任何资产零可达**（不是"授权后不可达"，而是默认拒绝） |
| **R3 访客** | 临时来客 | 能上网 | 仅互联网出口，禁止访问任何内网资源 |
| **R4 设备** | 手机/电视/IoT/摄像头 | 稳定接入 | 按设备类型划分：IoT 走独立 SSID/网段，隔离内网横向访问 |

> **关键产品决策**：R4 智能家居设备与 R1 家庭成员必须**分网段**。IoT 设备是被攻破概率最高的入口，绝不能与私有云同域。
>
> **关键产品决策**：R2 租客与家庭内网**不是同一张网上的两个 SSID，而是上下游关系**——软路由的 WAN 就位于租客所在网段。因此软路由 **WAN 侧入站必须默认拒绝**，不能依赖 NAT 造成的隔离假象；对 WAN 的例外放行必须收敛到"必要端口 + 必要源"。

## 4. 信任域与上游边界模型

两个受管信任域 + 一条不可信边界，默认互不可见：

```
┌─────────────────── 家庭域 LAN-A（自住楼层，含 IoT 子域）──────────────────┐
│  成员手机 / 电视 / 智能家居设备                                            │
│  可达：互联网、家庭服务（DNS/AdGuard）、自己的私有云目录                    │
│  不可达：私有云管理面、其他成员的私有目录                                    │
└───────────────────────────────────────────────────────────────────────┘
┌─────────────────── 私有云域 LAN-B（NAS + 服务）─────────────────────────┐
│  NAS / Home Assistant / AdGuard / 备份服务                               │
│  可达：互联网（仅必要端口）                                               │
│  不可达：被任何客户端直接横向扫描；仅暴露授权端口与授权账号                  │
└───────────────────────────────────────────────────────────────────────┘
┌────────── 边界：上游租客网段（不可信，不在软路由管辖内）──────────────────┐
│  出租楼层租客设备 —— 直接接在主路由下，与软路由 WAN 同处一个二层网络          │
│  策略：软路由 WAN 侧 input / forward 默认 REJECT；不做"上一级所以安全"的假设 │
└───────────────────────────────────────────────────────────────────────┘
```

实现要点（非本文档实施细节，但必须在设计阶段锁定）：

- 家庭域与私有云域以**独立 VLAN + 独立 SSID + 独立子网**（如 `192.168.31.0/24`）划分，软路由作三层网关
- 域间默认策略 `DROP`，仅白名单放行：DNS（53/853）、NTP、DHCP 与授权服务端口
- 私有云域禁止客户端间横向通信（AP/交换机侧开启端口隔离，或网段内 ACL）
- **上游租客网段视为不可信**：软路由 WAN 与租客设备同处一个二层广播域，可被 ARP 探测与端口扫描；WAN 侧默认 `REJECT`，例外放行必须带**端口 + 源**双重限制
- 访客域独立 SSID，只 NAT 出网

## 5. 功能需求

优先级：**P0 = MVP 必须**，**P1 = 核心体验**，**P2 = 深水区/增强**

> **服务范围声明**：本方案的全部服务只覆盖**软路由下游的家庭网络**。上游租客网段不在软路由管辖内——**限速、DNS 强制与广告过滤都无法覆盖租客设备**。这是拓扑决定的能力边界，不是实现疏漏，必须提前说明。

### F1 全屋网络加速 —— P0（定义待确认）

> **问题：这是全文档最模糊的需求。** "加速"至少 4 种可能，方向完全不同，必须先选：

| 选项 | 含义 | 技术手段 | 风险/成本 |
|---|---|---|---|
| A. 跨境访问优化 | — | 涉及合规边界 | **本方案明确不纳入范围** |
| B. 低延迟优化 | 游戏、视频会议不卡 | SQM/QoS 智能流控 + 缓冲区膨胀治理 | 低风险，该级别算力可承受 |
| C. 解析与路由优化 | 网页打开更快 | 本地 DNS 缓存 + 并行上游 + CDN 就近解析 | 低风险，收益明显 |
| D. 多线负载均衡 | 多条宽带聚合/故障切换 | mwan3 | 需要多出口，当前只有一条宽带 |

**建议 MVP 落地 B + C**（零合规风险、纯体验收益），D 待明确需求后再评估。

**用户故事**：作为家庭成员，我打开网页/看视频/打游戏时不应该感觉到"卡在网络上"。

**验收**：DNS 平均解析 < 30ms；开启 SQM 后满载下载时视频通话不卡顿（主观 + 丢包率 < 1%）。

---

### F2 全屋智能家居中枢 —— P1

**用户故事**：作为家庭成员，我用一个 App 就能控制不同品牌的灯、插座、窗帘、传感器，且**断网也能用**。

**范围**
- 部署 Home Assistant（容器化），作为唯一控制入口
- 跨品牌接入：优先本地协议（Zigbee / Matter / 局域网 API），厂商云接入作为兜底
- 定制化集成：私有协议/无官方集成设备，用自定义组件或抓包逆向其局域网 API 接入
- 提供统一的家庭助手入口（Web / 手机 App / 语音）

**硬约束（必须提前决策）**
- 4 核 4GB 内存下，HA 的 recorder 数据库会**快速吃满系统盘 overlay 分区** → **数据库与备份必须重定向到 NAS 挂载点**
- Zigbee / 蓝牙 Mesh 设备需要**实体网关硬件**，软路由无法凭空接入 → 需采购（如 Zigbee 协调器）
- 建议 IoT 设备独立 SSID + 独立网段，HA 侧通过 ACL 单点访问

**验收**：≥ 90% 的家电/灯具可在 HA 中控制；断外网后本地设备控制仍可用；HA 重启后 1 分钟内恢复。

---

### F3 全域广告过滤 —— P0（DNS 层）+ P2（抓包层）

**必须先把预期管理讲清楚**：这是一场分层的战争，DNS 层能赢一大半，剩下的赢不了。

| 层 | 手段 | 能拦什么 | 拦不到什么 |
|---|---|---|---|
| **L1 DNS 域名层（P0）** | AdGuard Home + 公开规则（广告/跟踪/恶意域名） | 网页广告、跟踪器、绝大多数 App 广告 SDK 的域名请求 | 与业务同域的首方广告、CDN 内嵌广告 |
| **L2 抓包点名（P2）** | 对目标 App 抓包分析 → 提取广告域名 → 回写黑名单 | 特定 App 的广告/推送域名 | 走 HTTPS Pinning 的 App |
| **L3 无法覆盖（明确不承诺）** | — | — | 视频前贴片广告、App 首方内嵌广告、电视端需装证书的场景 |

**产品原则**：抓包是**一次性分析手段**，用于发现域名，**不是长期 MITM 代理**。长期对家庭成员手机做 HTTPS 解密涉及证书安装与隐私边界，必须单独取得同意。

**用户故事**：作为家庭成员，手机和电视连上家里 WiFi 后，网页和 App 里的弹窗、横幅、跟踪明显变少。

**验收**：DNS 层拦截率 ≥ 15%；主流网站与 App 功能不受影响（误杀率 < 1%）；提供**一键放行**入口，家人可自助上报误杀。

### F4 家庭私有云与自动备份 —— P0

**用户故事**：作为家庭成员，我外出拍的照片/存的资料，回家连上 WiFi 就自动进到家里的盘，不用再买云会员，而且**别人看不到我的东西**。

**范围**
- 私有云：NAS 作为存储底座，对外只通过授权协议（SMB / WebDAV / 各端 App）暴露
- 多账号隔离：**每位成员一个独立账号 + 独立目录 + 独立配额**，互相不可见
- 自动备份：客户端在"接入家庭 WiFi"条件下触发增量备份（照片、视频、文档）
- 媒体中心：NAS 同时承载自建音乐服务器与影视库，家庭成员在外通过加密隧道直接访问，**不依赖第三方会员**
- 与上游边界联动：NAS 位于软路由内层，**上游租客网段对 NAS 零可达**（见第 4 章）

**必须承认的实现依赖（这是产品风险，不是技术细节）**
- iOS 原生"照片"不直接支持 SMB/WebDAV → 需要**快捷指令 + SMB** 或第三方备份 App
- Android 可用 FolderSync / Syncthing / NAS 官方 App
- **"连上 WiFi 自动备份"是客户端能力，不是路由器单方面能实现的** → 需要家人同意安装并授权 App

**验收**：备份成功率 ≥ 99%；接入 WiFi 后 5 分钟内完成增量同步；成员 A 无法访问成员 B 的目录（含直连 IP 尝试）。

---

### F5 远程访问（内网穿透）—— P1

**用户故事**：作为家庭成员，我在外面用手机流量也能看到家里 NAS 上的资料，或者直接播放自己的音乐与影视库。

**方案选型**

| 方案 | 前提 | 适用 | 评价 |
|---|---|---|---|
| **Tailscale / WireGuard**（建议） | 无需公网 IP，NAT 穿透 | 文件访问、媒体播放、远程桌面、管理后台 | 软路由已部署 Tailscale，**改造成本最低**，设备级 ACL 可控 |
| frp / 端口映射 | 需公网 IP + 端口开放 | 对外发布 Web 服务 | 暴露面大，家庭场景不推荐 |
| Cloudflare Tunnel | 需域名 | 仅 Web 服务 | 不适合 SMB 文件协议 |

**产品红线**：**NAS 的 SMB/管理端口绝不直接暴露公网**，远程一律走加密隧道（内网 IP 访问）。家庭成员通过共享节点或独立节点 + ACL 授权。

**验收**：远程访问可用性 ≥ 99%；从公网与**上游租客网段**直接探测 NAS 端口均不可达。

### F7 可观测与运维（原始需求没提，但必须有）—— P1

**用户故事**：作为管理员，我不用每次登 SSH 就知道家里网络健康不健康，出问题能立刻定位。

**范围**：软路由资源（CPU/内存/磁盘/温度）监控、AdGuard 与 HA 容器存活探测、DNS 与延迟曲线、备份成功率看板、异常告警（可推送到手机）。

**特别提示**：overlay 分区容量有限（约 10GB），**日志与监控数据必须设置轮转与上限**，否则会在几个月后静默撑爆磁盘——这是本项目最容易被忽略的"定时炸弹"。

## 6. 关键设计决策与权衡

| 决策点 | 选项 | 建议 | 理由 |
|---|---|---|---|
| 域间隔离实现 | 独立 VLAN / 独立物理接口 | VLAN + 独立 SSID | 复用现有硬件，无线侧也能隔离 |
| 上游租客网段 | 信任 / 不信任 | **视为不可信边界** | WAN 与租客设备同处二层网络，不做"上一级所以安全"的假设 |
| 软路由角色 | 下游二级路由（现状）/ 上移为主路由 | 保持现状；上移作为可选项评估（Q3） | 上移后租客可纳入统一隔离与限速，但单点故障范围扩大到全家 + 租客 |
| 广告过滤位置 | 软路由本地 AdGuard / 上游 DNS 服务 | 本地 AdGuard Home | 数据不出户，规则可自定义，配合抓包闭环 |
| 智能家居中枢 | 软路由容器 / 独立小主机 | 先容器，**内存吃紧则迁独立设备** | 4 核 4GB 是明确瓶颈 |
| 远程访问 | 隧道 / 端口映射 | Tailscale（已有基础） | 不依赖公网 IP，暴露面最小 |

## 7. 风险登记册

| # | 风险 | 影响 | 概率 | 应对 |
|---|---|---|---|---|
| R-1 | **软路由成为单点故障**（家庭网络 + NAS + 全部服务） | 高 | 中 | 配置版本化备份 + 一键恢复镜像；保留主路由直连降级路径 |
| R-2 | **4 核 / 4GB 内存 / overlay 分区容量有限** | 高 | **高** | HA 数据库与备份重定向到 NAS；日志轮转；评估加内存 |
| R-3 | 抓包去广告触及隐私与证书边界 | 中 | 中 | 仅对自有设备；一次性分析而非长期 MITM；需家人明示同意 |
| R-4 | AdGuard 误杀导致家人用不了某功能 | 中 | **高** | 一键放行 + 白名单机制 + 误杀上报通道 |
| R-5 | 自动备份依赖客户端 App，家人不配合 | 中 | 中 | 优先选系统级/低打扰方案；一次配置长期生效 |
| R-6 | 改网络结构导致全家断网 | 中 | 高 | 明确维护窗口 + 回滚预案 + 先小范围验证 |
| R-7 | 广告预期落差（前贴片仍存在） | 低 | 高 | **提前把 L1/L2/L3 边界讲清楚，不承诺拦不掉的** |
| R-8 | IoT 设备被攻破后横向渗透 | 高 | 中 | IoT 独立网段 + 禁止访问私有云 + 禁用 WAN 侧管理 |
| R-9 | **软路由 WAN 暴露在上游租客网段**（同二层，可被 ARP 探测与端口扫描） | 高 | 中 | WAN 侧 input/forward 默认 REJECT；例外放行收敛到端口 + 源；定期复核 WAN 侧放行规则 |
| R-10 | 服务范围被误解为"覆盖租客"（限速/去广告实际做不到） | 中 | **高** | 在方案与沟通中**明确声明服务范围**，不承诺覆盖上游租客网段 |

## 9. 待决策问题（需决策方确认后才能进入实施设计）

1. **"全屋网络加速"具体指哪一种？**（F1 的 A/B/C/D，或组合）
2. 多楼层是**同一台主路由 + 多个 AP/交换机**，还是每层独立设备？软路由与主路由之间是**有线**还是无线？自住楼层设备是**有线**接入软路由还是无线？
3. **是否考虑把软路由上移为主路由**（由软路由拨号、租客挂其下）？这样租客才能被纳入统一的隔离与限速管理，代价是单点故障范围扩大到全家 + 租客。
4. 运营商是否提供**公网 IPv4 / IPv6**？是否动态？
5. NAS 的**盘位与可用容量**？多用户账号、配额与 SMB/WebDAV 已由飞牛 OS 原生支持（已确认），仍需确认容量规划与冗余方案。
6. 家庭成员的**手机机型分布**（iOS / Android 比例）？是否同意安装备份 App？
7. **智能家居设备清单与协议**（WiFi / Zigbee / 蓝牙 Mesh / Matter / 厂商云）？是否愿意采购 Zigbee 网关等硬件？
8. NAS 的可见范围与配额策略：**仅管理员 + 家庭成员**？是否需要为访客开设临时账号？
9. 可接受的**维护停机窗口**？（改网络结构必然导致全家断网一次）
10. **预算**：是否允许升级软路由内存？（4GB 内存是硬瓶颈）
11. 是否允许对家人手机/电视做 HTTPS 抓包？（涉及证书安装与隐私，必须明示同意）
12. **上游主路由的管理权限**：软路由只是它的一个下游客户端，**无法约束租客流量**（限速、DNS 强制、广告过滤都覆盖不到）。能否与主路由侧协同，或由主路由侧承担租客侧的隔离与限速？

## 10. 附录：资源预算（粗估，需实测校正）

| 服务 | 内存 | 磁盘 |
|---|---|---|
| OpenWrt 系统本体 | ~300MB | 基础系统 |
| AdGuard Home | ~100–150MB | 规则文件 ~100–300MB |
| Home Assistant（容器） | ~600MB–1GB | 镜像 ~1GB，**recorder 数据库必须外置** |
| Docker 运行时 | ~50–100MB | 镜像空间 |
| Tailscale | ~50MB | — |
| **合计** | **约 1.2–1.7GB** | **约 2GB+（不含 HA 数据库）** |

> 结论：4GB 内存下**勉强可行但无余量**；系统盘虽为 120GB SSD，但 overlay 分区仅约 10GB（可用约 6GB），**HA 的 recorder 数据库必然吃满它**。建议 M1 阶段就规划：HA 数据库与备份目录挂载到 NAS 独立存储，并评估加装内存。
